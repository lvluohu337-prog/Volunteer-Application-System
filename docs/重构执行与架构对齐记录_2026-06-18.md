# 重构执行与架构对齐记录

## 1. 背景

本轮重构基于 `docs/总体架构说明_同事版_2026-06-17.md` 和项目当前健壮性检查结果展开，目标不是一次性推翻重写，而是按“每一步审核通过后提交推送”的方式，逐步降低项目变成难维护代码堆的风险。

- `agent.md` 只作为本地协作记忆，不进入云端提交。

## 3. 当前架构对齐情况

### 3.1 双阶段流程

同事版总体架构强调：

```text
画像/八字/专业方向启发 -> 成绩位次选科录入 -> 真实招生数据匹配 -> 志愿方案 -> 风险复核 -> 报告交付
```

当前项目已经具备后半段“真实招生数据匹配 -> 志愿方案 -> 报告交付”的工程基础；前半段“引流分析 -> 专业方向启发 -> 转化引导”已有画像分析能力，但还没有形成独立入口和强转化页面。

后续建议：

- 保留当前后台工作台能力。
- 新增面向家长/学生的第一入口页面，围绕出生信息、画像分析、专业方向做轻量引导。
- 在专业方向结果页引导补充分数、位次、选科和省份批次。

### 3.2 三档产品

当前正式产品配置已覆盖 `99 / 399 / 999`，并明确 `699` 为规划中产品，不作为正式交付档位。

已完成的工程支撑：

- 报告产品目录支持不同交付渠道。
- PDF / Word 导出链路可运行。
- 导出记录和下载留痕已接入。

后续建议：

- `99`：偏轻量画像 + 基础建议，减少正式志愿承诺。
- `399`：作为标准正式交付主线，重点完善推荐表和人工复核流程。
- `999`：再扩展深度复核、城市路径、就业迁移、考研路径等内容，不提前混入 MVP。

### 3.3 双评分体系

同事版总体架构要求区分：

- 画像适配评分：用于专业方向启发和解释。
- 录取适配评分：用于真实招生匹配、冲稳保分层和风险判断。

当前项目中：

- `portrait_service.py` 已承接画像推荐职责。
- `admissions_context.py` 和 `admissions_engine.py` 负责真实招生上下文与匹配决策。
- 报告页合规文案已明确画像只作解释层，不替代真实录取判断。

后续建议：

- 不要把八字/五行画像直接混进录取概率。
- 画像评分可以影响“专业方向展示排序”和“解释文本”，但录取判断仍以分数、位次、选科、招生计划、历史录取为主。
- 在报告 JSON 中分离 `portraitFitScore` 与 `admissionFitScore`，避免前端误读综合分。
